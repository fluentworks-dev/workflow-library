Before designing or writing, read: the repository's guidance file, whole; one or two existing implementations of the same kind, with their tests; the lint, format, type-check and pre-commit configuration and the CI workflow, to know which checks gate a merge; and the history of any code that looks deliberate (a guard, a retry, an odd constant). Reason: skipping it is the single most common cause of plans that look reasonable in isolation but produce awkward, divergent code.

- When the repository has a pattern, use it: do not introduce new patterns, abstractions, or naming conventions that are not already present in the codebase. Add one only when the task needs it, it is clearly better and it will repeat.
- When the repository uses a formatter, a template or a convention different from yours, switch to it the same day and do not argue.
- When the existing pattern is wrong and fixing it is larger than the task, propose the fix. Never add a second pattern beside it or migrate half of it.
- When writing a new or changed line, apply every style rule. Leave untouched lines alone, never sweep, and never add lint enforcement for a naming rule, because it forces the sweep. A file where old lines say `as e` and new lines say `as error` is the policy working. Refuse a sweep as a file-wide cleanup for a separate pull request.
- When your change orphans code, delete it in its own commit whose body names what is deliberately kept ("the YAML parser stays: the import job still uses it."). Leave dead code that was already there and mention it.
- When the thing to delete is a contract (a route, a parameter, a setting, a column), deprecate it first: it has consumers.
- When old code is below the bar, do not sweep it and never write a new instance: a one-letter name, a bare `except Exception` away from a process boundary, an unexplained `import` inside a function, HTML by string concatenation, SQL by interpolation, a `# noqa` that hides a finding, a monotonic clock compared against `0.0`, a hard-coded `/tmp` path or tenant identifier, a retry of every exception. Retry only transient failures, even where older code retries everything.
- When the work is a quick prototype or a one-off script, the rules still apply: it is new lines.
- When a repository's policy is unwritten (keep or delete design documents, a commit prefix, an environment code), read it from the latest merged examples and state what you inferred under "Decided for you". When a document and the live system disagree on a name (`prod` against `prd`), the live name wins.
