- When about to add a file, type, setting, mode, flag, layer or dependency, look first for the form that needs none: different configuration of what exists (the same worker on a different queue already solves the problem), a deletion (a fix that adds no new machinery), a primitive the platform or a sibling repository already has. Say what the simpler form removes, by name.
- When the need does not exist yet, do not build for it: skip a worker-count setting until a second worker is needed; write no reusable abstraction for one loader's query shape, and extract the pattern if a second use case appears. Extract by the rule on how to decide: a shared piece at the second use case, code repeated for one concept at its third copy.
- When declining to build for scale, give the number and the trigger: for example, the largest account holds well under the 1,000-item page limit, results are cached for 10 minutes, and the design is revisited if an account grows past that limit.
- When revising a design, remove a concept. A draft with more concepts than the last one justifies each.
- When a mitigation does not work, remove it the same day and fix the underlying cost. A throttle that does not cut the cost comes out the day that is found, and the repeated cost is cached instead.
- The operator exception in the rule on how to decide may also keep an unused capability on equipment a person operates, when its operators expect to need it again. Nowhere else.
- When a call needs its signature to be understood, make its arguments keyword-only: the keyword form does not require remembering the signature, and it lets a signature grow without reordering anyone's call.
- When a unit of configuration takes inputs, write every input out there, so nothing arrives by invisible inheritance and reading one unit file tells the whole story.
- When a value is deliberate, write it out even if it equals the default, so a reader sees it is a choice. Name every opaque identifier in a trailing comment.
- When two things must agree, define one and import it. A test asserts against the constant, not a copy of its value.
- When two things mean different things, give them separate types or settings even if they match today, and write why at the point of temptation: one response class per handler, a local enumeration that duplicates a backend's so the two deploy apart.
- When another service depends on a file name or a string, put a guard comment at the coupling point.
- When a name resists you, the concept is wrong or split: fix the model. One concept has one name repository-wide (an `order` is never a `purchase` elsewhere, and a loaded term such as `job` is avoided where the codebase already means something else by it). Qualify a name that enters a shared namespace, because there it is global to every team's data.
- When modeling data, prefer the flatter shape, a map keyed by the name clients look up, and nothing stored that the structure determines (no `id` field inside a map already keyed by it).
- When a rule must hold for every caller, enforce it in the layer every caller passes. A layer does not know its children's concerns. Pure logic sits apart from adapters.
- When choosing between shapes, take the one that hides more behind a smaller interface, and reject one where a piece of state has two writers, a task has two ways to be done, a list lives in two places, or a new flag must be kept in step with an old one.
- When an operation changes state and can be retried or interrupted, answer what happens when it runs twice and when it stops halfway. Derive each step from the state that exists. Order two writes so a failure between them repairs itself on the next run, and write the order down.
- When the choice is a correct data model with a migration or a heuristic (matching text, inferring a state), choose the data model. When that stored shape needs a migration, nothing settles it and it is costly to change later, it is the person's: put the choice in the question batch. Otherwise decide it.
- When performance is in question, act only where the path is hot or the data can grow: no repeated reads, no call per item in a loop, no unbounded list.
- When a list is filtered, sorted or paged, do it in the query, not in code after reading every row: the database is almost always the answer, because it scales, unless it cannot do it or there is a good reason not to. Where the database cannot, say why in a comment and bound the rows read.

In industry terms: YAGNI, Kent Beck's rules of simple design, Ousterhout's deep modules, Hickey's "Simple Made Easy", and Metz's "duplication is far cheaper than the wrong abstraction". The explicit inputs depart on purpose from removing repetition through includes.
