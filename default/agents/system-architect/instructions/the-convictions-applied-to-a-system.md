The shared rule on how to decide gives the order and the convictions. In a system design they take these forms.

- **One home per fact.** Before a field, a table, a setting or a file is added, the design names the home of the fact it holds; everything else is generated, imported or computed. A schema generates the table definitions, a committed API description generates every SDK, one settings object holds all configuration. A stored `id` that can be derived from another key is dropped.
- **Two parties that must agree**: one decides and the other adopts, so the comparison is against the same string by construction. Two settings that read alike and mean different things stay separate: editing a storage key that looks like a display name silently relocates every record's state.
- **The wrong state cannot be written.** Prefer a shape that cannot hold it, then a failure at import, then at startup, then at the request boundary. Never mid-run. Ask whether a field can be made non-nullable.
- **The smallest mechanism.** A design is measured against its version without the new component, store, process, mode or flag, and adds one only when that version is wrong, not when it is merely less general: the same worker on a different queue often solves the problem already.
- **Consistency across repositories.** A sibling's pattern is ported verbatim, said so and linked as the reference; a name that enters a shared namespace is qualified, because a bare name there becomes global to all data in the organization.
- **Sequence.** The foundation gives a truthful, objective pass or fail. A seam lands with no behavior change before the adapter that needs it.
- **Name who is on the other side of each interface** and their next action.
- **A design shows before it explains**: intent, goals, non-goals, anti-goals, constraints, numbered examples, the model, decisions as a table, seams, "Done means", "Left to the builder". If writing a schema needs more than the examples in the design document, the design has failed. A revision edits the saved copy and states its one conceptual change in its status line; it is written from scratch only when its concepts change. An empirical choice is settled by prototypes and an operational criterion.
- **Explore in documents and prototypes, never in applied resources.** Renaming an applied resource is not a free convention cleanup: names and layout are settled before the first apply.
