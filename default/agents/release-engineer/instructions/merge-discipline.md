- When you merge, squash: one pull request, one commit. The title is the subject, the host appends the pull request number, and the body lists the branch's commit messages. The default branch then reads as a changelog per pull request and a revert is one commit. No merge commit lands on a shared default branch. A method the repository configures wins.
- When the branch is behind, bring it up to date without rewriting it. A rebase and re-push is a force-push, and you never force-push. Where the repository squash-merges, merge the default branch in and push normally; the squash leaves the default branch the same. Where it requires a rebased branch, the rebase and the re-push are the person's step.
- A branch arrives in a fixed shape: one commit per task with its tests, fix-ups as plain commits named for what they fix, the removal of any working document found on it in its own commit, then review-response commits. Add to the end. Never reorder, fold or amend.
- When review asks for a change, add a commit whose subject names the round and enumerates the points ("Address the second review round on tests and docs"). No `fixup!` or `squash!` commits: the squash folds everything, and a separate commit shows the reviewer what changed.
- When you push after an approval, announce it before merging; the approval covered the code it saw. Name the new commit's hash and what it fixes, for example two issues a final run against the development environment found, and whether they also exist on the default branch.
- When the automated reviewer has commented, clear it; do not wait for it. Every thread gets a verdict word ("Fixed in" with the hash, "Declining", "Not a bug", "Deferred", "Partly") with a hash or a verified reason, in one pass, with one commit named for the round. Never merge over a thread with no verdict or a security finding with no answer.
- When the repository is shared, it waits for a human approval, and that wait is not shortened. A review the host requires must exist on the host. Never bypass a protection or use an administrator override; report a block as it was given.
- When a repository has several long-lived branches, check the base first: features to `develop` and hotfixes to `release` where that flow exists; an integration branch only for a multi-week migration, squashed in as one pull request. A pull request on the wrong base carries hundreds of foreign commits. Close a mis-based pull request within hours and reopen it on the right base.
- Never push to the default branch directly.
- Merge one pull request at a time, the next only when the default branch is green with the last. Use the merge queue where the repository has one. Never enable automatic merging: you merge when you have seen every condition true.
- Wait for checks with one watching command run by itself; never sleep in a loop or chain the wait after a push. Never make a check green by changing the check.
- Resolve a conflict by keeping both intents: what merged is settled, so fit this change around it. A merge with no conflict can still break (a function renamed on the default branch, a second migration on one table), so rerun the related checks after every update. Rerun only what the update touched: the checks that cover what came in, and the whole set when it changed a check, a dependency, a migration or a file this ticket touches. The in-practice instructions name each stack's commands, not a full rerun. Tests that run only by hand were run by Software Validation; rerun one here only when what came in touches it. A review covers the code it saw, not the code that lands.
