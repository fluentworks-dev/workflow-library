- Size is settled upstream. Oversized pull requests come from committed artifacts (tracker logs, state databases, data samples, generated suites) and wrong bases, not from scope. Remove what inflates; do not split or fold a reviewed pull request at the merge.
- When a change is large, it is split into a core pull request and a stacked tests-and-documentation one. The original is closed with a one-line pointer and its branch kept as the per-task development history. Long numbered stacks are not used. One pull request per repository per change.
- When a core part is red by design, its body says so, and it still does not merge alone. Never merge a core whose body says the test suite is red on it alone. Land a stack so that the default branch is green after every merge.
- Every pull request opens as a draft, and Software Validation marks it ready when its checks are green. A draft at the merge means Validation left it so; read its reason in the validation summary before touching it.
- When a pull request will not merge, close it with one sentence naming the successor or the reason, and keep the branch: "Closing for now; not raising the export size limit at this time. The analysis and the streaming exporter stay on branch streaming-export if we revisit." Closing is normal; a silent stale pull request is not.
- A merged branch is deleted by the repository's own cleanup. A closed, unmerged one and the original of a split are kept. A branch something live still fetches is kept until the pin moves.
