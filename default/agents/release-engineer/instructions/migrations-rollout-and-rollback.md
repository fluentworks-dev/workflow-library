A change ships only when the running system can serve before, during and after it. How the repository applies migrations (in the deploy before the new code serves, in a workflow after it, or by hand) decides what may merge.

- An additive migration (a new table, a nullable column, a constant default) may ship with the code that reads it only when it is applied before that code serves. When it would run after, or by hand and has not, merge nothing: every read would fail.
- A drop or a rename of anything the live system reads never ships with the code that stops reading it. The drop follows in a later pull request, because the old version serves until the deploy switches over.
- Indexes and other deploy-time facts are data applied by a script; the server never runs DDL.
- When a merge needs an operator, write the precondition and the post-merge steps into the pull request, in order, and state what a rollback loses when it is not symmetric. A rollback of the deploy keeps the schema, which is safe exactly when the migration was additive.
- When writing a script, make it idempotent and re-runnable with a dry run and bounded concurrency, safe beside the live service. A one-off backfill ships with the forward change and is deleted once run. Its proof is a count against the source: every source row accounted for, with 0 missing, 0 extra and 0 value mismatches.
- Promise only what the service can observe: where it has no metrics infrastructure, say so. Cost is right-sized in small pull requests; a changed schedule or size carries its price in a reviewer note.
- Decision records travel with the change: a "Considered but not changed" section, and "Known follow-ups" with any one-time data-loss caveat on upgrade spelled out. When the diff has such a caveat and the body lacks the sentence, add it.
- Deploying is not releasing. The merge reaches staging; production waits for a release and a slot swapped by hand. A switch that gates the change stays off unless the ticket says on, and never replaces expand and contract.
- When the default branch breaks after the merge: fix forward when the fix is one obvious change you can verify now; revert the squash when the cause is not understood within about fifteen minutes (a number chosen by feel); never revert blindly over an applied migration; restore a removed contract as deprecated when a consumer breaks; report an unhealthy deployment and leave the redeploy to the person; prove a failure that already existed on the parent commit and leave it.
