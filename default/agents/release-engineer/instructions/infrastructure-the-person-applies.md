- A person keeps every apply where no CI exists, bootstrap trust roots, resources that cannot be tagged, first applies (as a service principal, never as a person) and every destroy.
- When trust roots, untaggable resources or first applies that need special credentials are involved, the person applies from the branch before the merge, and CI must then find no changes. Destroys are never automated. Merging first would leave a default branch that describes infrastructure that does not exist.
- The merge condition is a plan at the current head that reports "No changes", and a body that says what was applied by hand ("Reviewer note: the container registry and network were applied by hand while the pull request was open"). Plan counts are acceptance criteria: "12 to add, 3 to change, 0 to destroy", then "must report no changes".
- A plan with a destroy or a replacement does not merge until the person has read that line. A concurrency group cancels a superseded plan, never a running apply.
- When a plan wants to replace an immutable resource for a convention cleanup, add an override that keeps the old name: renaming an applied resource is not a free convention cleanup.
- When code and cloud may have drifted, plan every environment first, align the code to what is live and name each drift, then add the change. Otherwise the apply silently reverts someone's fix.
- When a change renames or moves applied infrastructure, the name is settled in system-design.md and proven by offline tests before the first apply. Every change of naming scheme costs state moves and imports.
- A secret managed outside the tool sits under `ignore_changes` with a comment on what an unguarded apply would do (for example, lock out every user). A plan that touches it is a stop.
- Never leave a live account running from a pull request branch pinned to an unmerged head, which is fetchable only while that branch exists.
- When writing a runbook, give exact commands, expected plan counts, the acceptance condition and a symptoms-to-causes table, in the README. Commands are verbatim, with no task runner, and bootstrap steps are split into "Already done in this environment" and "Remaining (admin)". Write the recovery the day the failure is first seen, as for a credential left isolated, unbound and invisible even to its owner.
