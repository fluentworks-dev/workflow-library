Name the person, then write the outcomes that person needs.

- **An operator at a machine.** The system keeps running when something outside it fails: a failure in the cloud never blocks a run, and a side task never brings the process down. Write the one exception with its reason (a missing record that would silently detach a run from the request that started it must stop the start). "Finished" and "failed" are different events. A batch reports each failed item with its error and counts as failed when any item failed. One malformed item never hides the rest of a list.
- **A user of an application.** An error names the class of failure and the next action. What the person can act on is shown ("This item does not exist or you do not have access to it."); the detail of a server fault never is; a refusal never reveals whether the thing exists. A form keeps what was typed, and keeps a server error visible while it is corrected. Doing nothing is safe. Every control has an accessible name.
- **A non-technical user of a tool or a platform.** The promise is that no cloud or operations knowledge is required. Ask exactly one question and infer the rest. Fix before speaking: the user cannot debug, so when something fails, try to fix it yourself before saying anything, retry a given fix a bounded number of times (about two or three), and always speak about the domain in plain language. Never show a stack trace; every error gives the domain, what happened and what to do ("The name 'X' is already taken by another app." / "Pick a different app name."). Fail at the first step that can detect the problem. Split the irreversible step from the reversible one, say in plain language exactly what would be published, and confirm the cost before anything paid for exists. Setup can be run again: a step already done counts as success, and setup continues. Every document names a human to go to.
- **An engineer or a system downstream.** Nothing they rely on changes without warning: deprecations instead of removals, old names kept as aliases, a changelog per producer version before readers change. A reduced view keeps the same shape with fewer fields, so one pipeline serves both.
- **A future maintainer, human or agent.** They can act without asking: what is live and what is known to be broken is written where they read it; a failure learned today has its recovery steps today; an opaque identifier has its meaning beside it.
- When real use produces findings, scope the next round from them only: a table by severity where each change maps to something that actually went wrong during that run, plus a "Considered but not changed" list.
- Developer experience is the same instinct turned inward. Scope it as a product, with a goal, an outcome and a measure.
