The agreement keeps a fixed shape: Goal, In, Out, Anti-goals, Outcome, Seams, Extent.

- **Out (non-goals)** are things someone could expect and will not get, each with its reason. A non-goal without a reason gets reopened.
- **Anti-goals** say "never, and a reviewer should reject a change that does it", one checkable sentence each: "A second place to define a property."; "Do not default a blank name to anything."; "No environment details in the catalog of systems: a system is a logical node, not a deployment."
- **One fact, one home.** When an outcome asks for a figure that follows from what is recorded, scope "show the computed figure", never a field to enter it or a stored copy that can disagree: a stored identifier that can be derived from the key it is stored under is dropped.
- **Different meanings stay apart.** When two requirements look alike and mean different things, scope two things and write the difference where someone would merge them. A missing campaign code (send the email, attribute it to nothing) and a disabled send switch (do not send) stay two settings. Two things that read the same today and answer to different owners will diverge.
- **Seams** are deferred work with a contract, named so nobody builds around them: what is left for later, and what must stay true so it can be added. A deferral with no seam is forgotten or blocked.
- **Outcomes** are observations, not activities ("Done means"), numbered O1, O2, ... and never renumbered. They include what a person sees when there is nothing, too much, something invalid, or a dependency that is down.
- When a case is abnormal (the file exists, the value is too large), the outcome is a refusal someone sees, never a silent overwrite or a truncation: it is better to stop with an error so that someone can take a look. When waiting is normal use, the outcome is a state, not an error.
- When a product rule is undecided (who may change something, which values are allowed), ship the read path and gate the write path, with the sentence that says so, for example: values are displayed only, not created, until the product rule is decided. A read path can be withdrawn without anyone losing work; a write path creates data the eventual rule must honor. Name what the write path will need as a seam.
- When the product may meet a value it does not know, scope "show it as it is"; the owning system decides which values exist. A field fixed after creation is shown grayed, marked as one that cannot be changed, not hidden. A blank optional field sends nothing, so the default of the owner applies. A rule that belongs to another system may be suggested here and never required.
- Name a ticket or a branch for what changes, not where: `reduce-search-latency` beats `update-search-code`. A concept you cannot name cleanly is two concepts, or the wrong one.
