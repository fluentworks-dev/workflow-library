Scope names what is touched and who relies on it. Design surveys the call sites and proposes the change.

- Repositories are the one thing never to infer. When the project names one repository and the ticket none, that is the repository. When the change forces work in a repository nobody named, flag it to the person; never add it or drop it silently.
- Name every contract the scope touches and its consumers: an interface, a stored shape, an event, a file format, a configuration name, a status code, an error text another system matches on, a name in a shared namespace (a name that is global to all data in the organization). Say whether it is extended, changed (a new version or a fallback) or removed.
- When anything a consumer might use is removed: search the sibling repositories and name each caller, deprecate first, move each consumer in its own change, remove in a later ticket. A set of old routes removed after a search can still have a caller the search missed, and then the route comes back as deprecated. "No caller found" is a claim to verify. Dead code with no consumer is deleted, not deprecated: the distinction is who can be hurt.
- When a consumer disputes a contract, settle it during scoping. A contract merged over an open objection is renegotiated once it has consumers.
- When more than one repository changes, write the order: the owner of the contract, then its consumers, then the surface people see. One pull request each, and one name for the change everywhere.
- Operations are scope inputs. Write the preconditions and their order ("seed, then deploy"), the steps after the merge and who runs them, what happens to existing data (old records keep working without a rewrite where possible), every environment the outcome must hold in (a separate government or regional cloud partition, for example), and the base branch when it is not the default branch.
- Be honest about what can be observed: when there is no metrics system in the service today, say so and name the first counter to add when one lands. Never promise a measure the system cannot produce.
- When the scope touches identity, permissions, secrets or personal data, say so, so that System Design runs its security pass. No security finding is left without an answer.
- When a finding belongs to another repository or another owner, record it as a known gap where that owner reads it (the status paragraph of its README) and move on. Do not widen the scope, and do not let it vanish.
- When you find a problem on the way in the same repository: under about two hours of agent time, it is "also fixed here", with no question; larger and part of what this ticket delivers, it goes into the session's one batch with its cost, doing it now first; larger and not part of it, it is one line under Out, with no question.
- Decision records travel with the change: what was decided, what was decided without asking, what was considered and not changed.
