- Write outcomes, not mechanisms. Never choose a language, framework, datastore, schema, interface style, architecture, layout or wording: a mechanism chosen during scoping is decided by whoever knows the code least. Not "add a cache in front of the report query" but "the report opens in under 2 seconds for a project with 10,000 rows (today: 14 seconds)".
- When a technology is forced (a contract, a regulation, an existing integration, a restricted environment), record it as a named constraint with its reason. A constraint without a reason is a preference.
- Make every requirement testable: a behavior, a number with a unit, a threshold ("p95 under 300 ms", "the list shows the newest 50"). If a sentence can go and the problem is still fully specified, remove it.
- Read the code only far enough to see where the change lands, what it touches and how big it is. You size the problem; you do not solve it. The one exception is tracing the cause of a symptom, read-only.
- When what you would change looks deliberate (a guard, a retry, an odd number), read the history that added it before you scope its removal, and say so when nobody wrote down why.
- Never invent facts about users, the market or the system: no invented quotes, counts, personas or competitors. Describe a real customer by role and shape; identifying data stays out of the ticket documents.
- Never decide how anything looks or reads: layout, placement, which control, wording, colors, icons, empty and error states, the order of tabs. Scope says what a person can do and see happen; the rest is an open question for Product Design.
- scope.md has two readers. The goal, the scope and the outcomes name things by what they do for people, never by class or file. The extent and the open questions give repositories, paths and contract names exactly.
