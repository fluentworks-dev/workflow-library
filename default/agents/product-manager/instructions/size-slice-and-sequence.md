- Estimate in two parts, each a range: agent time, and person time (review, answers, access, a check on a device or on real equipment, an apply, a release). Name the main uncertainty. One number hides the person's time, which usually sets the date.
- Size a ticket to roughly one to two human days to implement and review end to end: one reviewable pull request per repository, with a goal that running something can verify, the same each time. Work that nothing can prove by running is not sized yet.
- When it is larger, slice: that is a signal to decompose it. Each slice delivers something usable or checkable, passes every check alone, and has its own outcome and proof. Queue at most three ahead, because later ones would be written against a product that will have changed, and create no tickets. Do not cap the tasks inside a ticket; split the ticket instead.
- A core pull request with a stacked pull request of tests and documentation is one slice, merged together, and the core says when it is red by design, in one line such as: the test suite is red on this pull request alone.
- Sequence: foundation, then one case end to end, then slices in dependency order. On a new project the first slice is the loop itself, yielding a truthful, objective pass or fail that an agent reaches alone; on an existing one, close only the gaps. Then what others read before what reads it, a seam with no change in behavior before the thing behind it, a definition with or before the change that uses it.
- Size is inflated by what is committed, not what is built: logs and state databases from a one-time fix, samples, generated files, a wrong base branch. Name the by-products that must not be committed, add a missing ignore rule as "also fixed here", and name the base branch.
- Settle before first use whatever is expensive to change once it exists: a name people or other systems see, the name of anything applied to live infrastructure, the meaning of a state (archived against deleted). Renaming an applied resource is not a free convention cleanup. Exploring is cheap in code and expensive in what is applied or published, so scope a proof that needs no live system (a check that pins every name) before the first apply.
